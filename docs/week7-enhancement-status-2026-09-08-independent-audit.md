## What remains, least work first

1. **#1 pickup/delivery, #9 borrower categories, #10 other equipment — the mobile half only.** All three are complete on the backend and in the admin panel and blocked on the same single pass over `Mobile/lib/screens/borrow_equipment_screen.dart` plus `ApiService.submitBorrowRequest`. This is already scoped as commit 5; see `docs/session-note-2026-09-08.md`.
2. **#13 verified safety information — one field on one mobile model.** The backend sends `verified` and the admin sets it; `Mobile/lib/models/info_material.dart` just has to parse it and the library card has to show a mark. Smallest remaining item on this list.
3. **#15 placeholders — one dialog.** `ServiceRequestQueue.vue`'s walk-in create dialog is the bulk of the gap, plus three stragglers. Mechanical.
4. **#10 procurement reference — a naming and surfacing decision, then small work.** The data is already captured; what is missing is presenting it as a procurement reference (a label, and wherever MDRRMC expects to read it). Needs the intent settled before the code.
5. **#3 due-date reminder — new infrastructure.** No scheduled command, no notification layer, no delivery channel. SMS exists (`PhilSms`) and could carry it, which makes this cheaper than #6 but still a build.
6. **#5 multi-role accounts — a design decision first.** Two of four roles exist and the single-tier model is currently deliberate and documented (`AdminController.php:20`). Adding staff and barangay tiers means a permission model, not just an enum.
7. **#8 organization-routed services — schema, policy and UI in all three layers.** Nothing exists. Needs to know what an organization *is* first, which is the same unanswered question behind #9's free-text org name.
8. **#6 push while closed — largest.** Push provider, device-token storage, server send path, platform config on both OSes, and a delivery policy.
9. **#11 places API — largest with an external dependency and a running cost.** Affects every location field in all three layers, and needs a key, a billing decision and an offline fallback for an app whose users are often on poor connections.

## Where the code does something different from Form 1

**#9 — Form 1 says three categories, the code has two.** Form 1 reads "individual and organization as borrower categories, not just resident", which names **Individual, Organization and Resident**. The enum is `['Resident','Organization']`; `Individual` was considered and deliberately dropped, and a test (`EquipmentBorrowingBorrowerTypeTest::test_an_unknown_borrower_type_is_refused`) actively refuses the word. The reasoning: `resident_id` is a required non-nullable FK on `tbl_equipment_borrowing`, so every borrower is already an account holder and an `Individual` row would be indistinguishable in the data from a `Resident` one. Representing a genuine non-resident walk-in means making `resident_id` nullable — a larger change that was not made because MDRRMO has not asked to serve non-residents.

This is a defensible reading, but **it is a departure from the stakeholder wording and should be confirmed with them rather than assumed settled.** If they meant a walk-in who holds no account, the current schema cannot express it.

**#10 — the text is stored, but nothing records it as a procurement reference.** Form 1 says "recorded as an MDRRMC procurement reference". `other_equipment_text` captures what the resident typed and the release guard refuses to hand out an uncatalogued item, which is the *control* half. The *recording* half is absent: the strings "procurement" and "MDRRMC" do not appear anywhere in the codebase, there is no reference number, no procurement status, and no export or view that presents these rows as a procurement queue. The admin panel treats the text purely as a substitute item name (`EquipmentBorrowingView.vue:1013`). Storing the text is not the same as recording it as a reference, and this item should not be closed on the strength of the column existing.

**#5 — the code's single-tier model is deliberate and contradicts the item.** `AdminController.php:20` documents "no super-admin tier, deliberately… a role column that only ever holds one value is a tier nobody administers." That decision predates this list. It is not an oversight, but it does mean item 5 cannot be delivered without revisiting it.

**#4 — narrower than Form 1 by design.** Form 1 says "capture equipment photos before release and on return". The implementation refuses a release photo while the record is still `Pending` or `Approved` — the earliest it accepts one is `Released`. So "before release" in the strict sense is not possible; the photo is taken at the moment of release, not ahead of it. Flagging it because the wording differs, though the practical result is the same handover record.
