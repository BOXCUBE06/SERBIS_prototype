## Later the same day (local only, the last seven commits)

**Accounts table** (the first ten commits, summarised): sortable headers with default Name A-Z, row selection with a bulk bar, per-row Edit and Activate/Deactivate buttons, the compact filter bar (`styles/filter-bar.css`) with a fade and 4px slide on its menus, and the account type tag on the Name cell's second line so names wrap to two lines.

**Equipment Borrowing page height** (`61f62445`, then `3c174316`). Symptom: a window scrollbar and a strip under the shell at 1366×768. Cause was not `100vh` or the table height: the `.sr-only` live region at `EquipmentBorrowingView.vue` is `position: absolute` with no positioned ancestor inside the shell's scroll box, so it anchored to the app root at the end of the content and made the document taller than the viewport whenever the page overflowed. Fix: `.inner-wrapper { position: relative }` in `App.vue`, so absolute children anchor inside the scroll box and its overflow clips them. Measured in Brave before the shell-level move (page-level rule): window scroll 0 at 1920×1080 and 1366×768 on both tabs, down from 281 and 209 px at 1366×768. At 1366×768 the shell still scrolls internally (293 px Board, 221 px History) because the table reserves a full page of rows; that is the shell's designed scroll and was left alone. `ConductionRequestView`, the only other `DataTablePage` view, had no window scroll at either size. **`3c174316` (shell-level) was not re-measured.**

**Brave dialog-dropdown fix** (`e5cfe215`, `680be8e9`, `930b051d`). In Brave, a select or autocomplete inside a `v-dialog` (Account type and Barangay in the account dialog, Service and Head of the Family in Log Service Request) opened detached toward the bottom-right, only for a real mouse click (Playwright's synthetic clicks never reproduced it, and neither did a clean Playwright-launched Brave). A window resize snapped it into place, and turning the menu transition off (`daaf39be`, reverted in `8c1b8546`) did not help. Menus inside a dialog take Vuetify's fixed-position path (`position: fixed`, viewport coordinates) because the dialog overlay is `position: fixed`; page menus (the Accounts filters) take the absolute path and were never affected. `plugins/overlayReposition.ts` watches `.v-overlay-container` with a `MutationObserver` and dispatches a synthetic `resize`, which Vuetify's connected location strategy already listens to: one two frames after any menu opens, and for menus in a dialog one more on the next pointerup/click and one when the enter transition ends (250 ms fallback), at most three per open, cancelled if the menu closes. With the plugin on, real clicks in Brave open correctly; with it switched off (`window.__noReposition`, an injected test flag, never in the source) the bug returned. `930b051d` (the extra recomputes) was tested in the user's normal Brave: Account type in New and Edit account, and Service and Head of the Family in Log Service Request, all open correctly. Chromium checks: menus open under their field on repeated opens, Barangay flips above when it does not fit (correct).

**Local dev.** The API is now served through XAMPP Apache on `:8000` (vhost appended to `C:\xampp\apache\conf\extra\httpd-vhosts.conf`, backup `httpd-vhosts.conf.bak-serbis`) instead of the single-threaded `php artisan serve`; the panel's `.env.development` (`http://localhost:8000/api`) is unchanged. Sluggish requests turned out to be MariaDB 10.4.32 (XAMPP) hung on an InnoDB dictionary-latch semaphore from about 15:35; the server crashed itself on the 600-second watchdog at 15:51, crash recovery was clean, and `CHECK TABLE` came back OK on `serbis_test_db` and `serbis_phpunit`.
